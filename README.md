# Null Talisman — заказы поставщикам

Проект HackAlem AI 2026 для кейса «Электрокомплект»: объяснимый расчёт
пополнения склада. Разовые крупные продажи завышают закупку, а отсутствие
товара скрывает спрос. Приложение учитывает эти эффекты, сезонность, рост,
остатки, поставки в пути и ограничения поставщиков.

Менеджер выбирает склад и категорию, получает рекомендации по поставщикам,
проверяет график и обоснование, правит количество, утверждает заказ и скачивает
XLSX/CSV. Автоматической отправки поставщикам нет. Экспорт предназначен для
дальнейшего импорта; прямая интеграция с конкретной конфигурацией 1С не заявляется.

План работ на хакатон: [docs/PLAN.md](docs/PLAN.md)

## Запуск

Python 3.11+; команды из корня репозитория в активном виртуальном окружении:

```bash
python -m pip install -r requirements.txt
python -m streamlit run app/streamlit_app.py
```

Открыть локальный адрес, который напечатает Streamlit. При отсутствии
`data/demo/sales.csv` интерфейс сам запускает `python -m data.generate`.
Генератор создаёт восемь CSV с синтетическими данными (seed 42), 153 товара,
два склада и шесть поставщиков. Существующие демофайлы UI не перезаписывает.
Можно загрузить собственные CSV/XLSX по [контракту](docs/PLAN.md#3-контракт-данных-фиксируем-в-13001320-потом-не-трогаем).

## Архитектура и методология

Один процесс Python без БД и отдельного API:

`Streamlit → engine.io → demand → forecast → replenish/pipeline → UI → утверждение JSON → engine.export`.

- `engine.io`: проверка схем, приведение типов, хеширование клиентов, разворачивание комплектов BOM. Дата расчёта ограничивает историю.
- `engine.demand`: разовые заказы определяются одновременно по robust-z >6, объёму >30% медианного месячного спроса и клиенту с покупками не более чем в двух месяцах. Исключается превышение над медианой строки.
- Месячный спрос корректируется на доступность товара. При доступности <50% используется медиана ряда; восстановление ограничено тройной медианой. Текущий незавершённый месяц исключается из обучения.
- `engine.forecast`: месячная сезонность SKU/категории, устойчивый тренд Theil–Sen, отдельный плановый прирост менеджера. Для короткой и прерывистой истории используются упрощённые оценки. Модель математическая, без LLM.
- `engine.replenish` / `pipeline`: прогноз на срок поставки + цикл заказа, страховой запас, остатки, поставки в пути, упаковка, MOQ и срочность.
- `app/orders.py`: автор, время и неизменяемый снимок утверждённого заказа. `engine.export`: XLSX/CSV этого снимка, включая ручные изменения.

Дата и прирост в графике совпадают с расчётом заказа. Полный годовой прогноз
и независимая проверка на трёх отложенных месяцах доступны на странице «Проверки».
Она не меняет рабочие данные или утверждённые заказы.

## Конфигурация и хранение

Обязательных секретов нет. Переменные перечислены в `.env.example`:

- `CLIENT_HASH_SALT` — необязательная соль хеширования клиентов; без неё используется демонстрационная константа. Задаётся переменной окружения процесса; `.env` автоматически не загружается.
- `AI_API_KEY` — зарезервирована для опционального LLM; в текущем приложении не используется.

Нужны права записи в `data/demo/` и `data/orders/`. CSV демо, JSON утверждений,
виртуальные окружения и секреты исключены из Git. Сохранённые JSON переживают
перезапуск; восстановление состояния редактора из журнала пока не реализовано.

## Проверка и демо

```bash
python -m pytest -q
```

Тесты создают данные в отдельных временных директориях. Проверяются контракты,
приёмочные сценарии, UI с реальным ядром, ручная правка, утверждение и содержимое
XLSX/CSV. [Подробности интерфейса](app/README.md), [демо и питч](docs/DEMO.md).

Ручной сценарий: выбрать демоданные и 23.09.2026 → «Рассчитать» → открыть
«Показать обоснование и график» → изменить количество → указать имя → утвердить →
скачать XLSX. После следующей правки экспорт блокируется до повторного
утверждения. На странице «Проверки» нажать «Прогнать все».

Уточнение к первоначальному плану: stockout-проверка сравнивает восстановленный
прогноз спроса (`forecast_horizon`), как приёмочные тесты команды. Рост итоговой
потребности (`need_raw`) не гарантируется: сглаживание спроса может снижать
страховой запас. Это отличие явно обозначено в UI. Другие ограничения:
закупочных цен в исходном контракте нет, поэтому сумма в тенге не рассчитывается;
показатели качества на синтетике не доказывают качество на данных партнёра.

## Зависимости и сторонние компоненты

Общие ограничения версий находятся в `requirements.txt` и `app/requirements.txt`.
Используются pandas и numpy (таблицы и расчёт), Streamlit (UI и AppTest),
Plotly (графики), openpyxl (XLSX), pytest и pytest-cov (тесты).
Данные синтетические, генерируются `data/generate.py`. Внешние модели, LLM API
и сторонние датасеты в рабочем сценарии не используются. При разработке
использованы AI coding tools.

## История интеграции

Работа из ветки `codex/nikita-core` включена в `main`: загрузчик и графики движка соединены с UI команды.
Используются реальные модули расчёта из `main`; первоначальная заглушка заменена.
Инструкции интерфейса: [app/README.md](app/README.md).

Проверено в локальном Python 3.12 с зависимостями из `requirements.txt`.
Команды PowerShell из корня репозитория:

```powershell
$env:PYTHONUTF8 = '1'
.\.venv\Scripts\python.exe -m pytest -q
```

Тест чтения журнала использует UTF-8 явно; настройка выше оставлена как рабочий пример окружения Windows.
Приёмочные тесты создают свежие данные во временном каталоге; содержимое
локального `data/demo/` не влияет на них. Генератор и исходные материалы
заказчика в этой интеграции не перезаписываются.

История проверок: [TDD evidence](docs/tdd/nikita-first-checkpoint.tdd.md).
