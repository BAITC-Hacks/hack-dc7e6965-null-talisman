**Трек:** HackAlem AI · кейс ТОО «Электрокомплект» (ekt.kz): автоматический расчёт заказов поставщикам для пополнения склада.
**Окно:** 23.09.2026, 13:00–18:00 (5 часов). **Команда:** Абдуали, Никита, Амир.
**Цель:** одно рабочее end-to-end приложение, в котором каждый из 5 must-have можно **показать и проверить за 30 секунд**.

## 0. Что строим (одним абзацем)

Менеджер закупа открывает веб-приложение → выбирает склад/категорию → жмёт «Рассчитать» → получает таблицу рекомендованных заказов, **сгруппированную по поставщикам**, с количеством, срочностью и **текстовым обоснованием** по каждой строке → при необходимости правит количество → **утверждает** заказ поставщику → выгружает XLSX/CSV для загрузки в 1С. Ничего не отправляется поставщику автоматически.

### Что берём из слов оператора, а что нет

| Боль оператора | Берём? | Как это выглядит у нас |
|---|---|---|
| «Нет актуальной информации, узнаём по телефону» | да | Колонка «в пути» с ETA; **просроченная поставка** (ETA прошёл) подсвечивается и помечается в обосновании |
| «Предупреждает о задержках» | да | Срочность «Критично: закончится DD.MM, раньше, чем придёт поставка» |
| «Документы вручную, ошибки» | да | Экспорт утверждённого заказа в XLSX/CSV в формате для 1С, лист на каждого поставщика |
| «Объяснять сложно, почему так» | да | Обоснование по каждой позиции + график «история → очищено → прогноз» |
| GPS машин, водители, маршруты, уведомления клиентам | **нет** | Не наш трек. Одна фраза в питче: «следующий шаг — связка с TMS» |

## 4. Алгоритм (для Абдуали и Никиты)

Расчёт ведём по паре (sku, warehouse), ряд помесячный. Все пороги лежат константами наверху модулей, чтобы на демо их можно было показать и покрутить.

### Шаг 1. Загрузка и обезличивание (`io.py`)
- `client_id` → `sha256(salt + id)[:10]` сразу при загрузке, дальше в коде только хэш. Соль берётся из env, по умолчанию константа. Это закрывает требование о приватности.
- Валидация: обязательные колонки, типы, даты парсятся, `qty` числовое. Ошибки собираем списком и показываем в UI; стектрейс пользователь не видит.
- Отбрасываем: дубли, `qty==0`, даты в будущем. Возвраты (`qty<0`) вычитаем из продаж того же месяца.
- **BOM:** продажи `parent_sku` разворачиваются в спрос на `component_sku × qty_per`. Компоненты при этом сохраняют собственные прямые продажи.

### Шаг 2. Разовые крупные заказы (`demand.py`) — must-have 4
«Строка заказа» = сумма `qty` по (date, client, sku, warehouse). Строка считается **разовой**, если выполнены все три условия:
1. **Выброс:** robust-z = (q − медиана) / (1.4826·MAD) > **6**. Если MAD = 0, берём среднее абсолютное отклонение, а если и оно 0, то 1.
2. **Существенность:** q > **0.3 ×** медианного месячного спроса по sku (иначе у редких товаров шум будет помечаться как разовый заказ).
3. **Нерегулярный клиент:** клиент покупал этот sku не более чем в **2** разных месяцах. Так крупный *постоянный* оптовик не выкидывается, а случайный проект выкидывается.

Помеченную строку не удаляем целиком, а **обрезаем до медианы строки** по sku: клиент остаётся «обычным покупателем», а исключается только сверхобъём. Сумма исключённого записывается в `oneoff_excluded`, а даты и клиенты сохраняются для обоснования и графика.

### Шаг 3. Месячный ряд и упущенный спрос — must-have 3
- Агрегируем очищенные продажи по месяцам. Месяцы без продаж заполняем 0.
- Для каждого месяца доля доступности `f = (дней в месяце − дней stockout) / дней в месяце`.
- `f ≥ 0.5` → `clean = actual / f`.
- `f < 0.5` → месяц почти пустой, делить опасно, поэтому `clean = ожидаемое` = уровень × сезонный индекс этого месяца (двухпроходный расчёт: сначала модель строится без таких месяцев, потом они заполняются).
- Ограничитель: `clean ≤ 3 × медиана ряда`.
- `lost_demand_added = Σ(clean − actual)` по месяцам со stockout.
- Последний неполный месяц масштабируем на число прошедших дней.

### Шаг 4. Прогноз (`forecast.py`) — must-have 2
Мультипликативная модель: **спрос(месяц) = уровень × (1 + тренд)^h × сезонность(месяц) × (1 + прирост)**.

- **Сезонность:** для каждого месяца года берём отношение спроса к центрированному 12-месячному скользящему среднему и усредняем по годам. Нормируем так, чтобы среднее было 1, и клипаем в [0.3, 3].
  - Истории < 24 месяцев или sku с малыми объёмами → индекс **категории** (пул всех sku категории).
  - Иначе смесь `w·S_sku + (1−w)·S_cat`, где `w = min(1, лет_истории / 3)`.
- **Уровень:** среднее десезонализированного ряда за последние 6 месяцев.
- **Тренд (устойчивый рост):** наклон Theil–Sen (медиана попарных наклонов) по последним 12–18 десезонализированным месяцам, в %/мес от уровня. Применяем, только если наклон одного знака в обеих половинах окна (так он «устойчивый», а не один всплеск) и |наклон| > 1%/мес. Клип [−5%, +10%]/мес.
- **Прирост:** `growth_pct` категории от менеджера (контракты, промо). Это отдельный множитель к тренду, в UI правится слайдером.
- **Прерывистый спрос** (> 50% нулевых месяцев): уровень = среднее ненулевых × доля ненулевых месяцев, сезонность не применяем, флаг `intermittent`.
- **Новинка** (< 3 месяцев истории): уровень = среднее по имеющимся месяцам, `confidence=low`, флаг `new`.
- **Backtest:** последние 3 месяца прячем, прогнозируем, считаем WAPE нашей модели и наивного среднего. Результат идёт в `confidence` и на страницу «Проверки» как доказательство, что сезонность работает.

### Шаг 5. Потребность и заказ (`replenish.py`) — must-have 1 и 5
```
horizon_days      = lead_time_days + review_days
forecast_horizon  = Σ прогноз по дням горизонта (месячный прогноз / дней в месяце)
σ                 = std остатков модели (месячный)
safety_stock      = z(service_level) · σ · sqrt(horizon_days / 30)
in_transit        = Σ qty в пути с ETA ≤ today + horizon_days
                    (ETA < today → считаем, но transit_overdue=True)
need_raw          = forecast_horizon + safety_stock − on_hand − in_transit
recommended_qty   = 0, если need_raw ≤ 0
                    иначе max(moq, ceil(need_raw / pack_size) · pack_size)
```
`z` берём из `statistics.NormalDist().inv_cdf(service_level)`.

**Срочность:**
- `days_of_cover = on_hand / дневной прогноз`
- `critical`: `days_of_cover < lead_time_days`, то есть кончится раньше, чем придёт новая поставка
- `high`: `(on_hand + in_transit) / дневной прогноз < horizon_days`
- `normal`: остальное при `recommended_qty > 0`
- Позиции с `recommended_qty = 0` в список заказа не попадают, но видны по фильтру «все позиции».

**Шаблон обоснования** (части без данных выпадают):
> «Прогноз на 45 дн. (срок поставки 30 + цикл 15): 820 шт. Сезон ×1.35 (пик — октябрь), рост +3%/мес. Исключён разовый заказ 1 200 шт (клиент a3f9…, 12.03). Добавлено 140 шт упущенного спроса (18 дн. без товара в мае). Страховой запас 95 шт (95%). Остаток 210, в пути 300 (ETA 01.10, **просрочено**). Заказать 420 → округлено до 450 (упаковка 50). Критично: закончится 05.10, поставка придёт не раньше 23.10.»

### Шаг 6. Утверждение и экспорт
- В UI: `st.data_editor` → менеджер правит `recommended_qty`. Исправленные строки получают пометку «изменено вручную» с исходным числом.
- Кнопка «Утвердить заказ поставщику X» пишет `data/orders/{date}_{supplier}.json` со статусом `approved`, автором (поле ввода имени) и временем. **Автоотправки нет** (требование трека).
- Экспорт XLSX: лист на каждого поставщика, колонки `Артикул; Номенклатура; Склад; Количество; Ед.; Поставщик; Срочность; Обоснование`. Загружается в 1С через «Загрузка данных из табличного документа». Плюс CSV (`;`, UTF-8 BOM) на случай старой конфигурации.

## 5. Синтетические данные (`data/generate.py`, Никита)

Детерминированно, `seed=42`, генерация меньше 10 секунд. Приложение само вызывает генератор, если `data/demo/` пуст.

- **~150 sku**, **8 категорий** электротехники: кабель, автоматические выключатели, розетки/выключатели, светильники, щиты/боксы, лампы, УЗО/дифавтоматы, кабель-каналы.
- **6 поставщиков**, lead time 7–60 дней, цикл 7–30 дней, у части MOQ и упаковка.
- **2 склада**, **3 года** дневных продаж, **~300 клиентов** (ID сразу вида `C0001`, хэшируются на загрузке).
- Паттерны: кабель и щиты с летним строительным пиком; светильники и лампы с зимним пиком; у части sku рост +2–4%/мес; у части прерывистый спрос; несколько новинок.
- Шум Пуассон/отрицательный биномиальный, цены ±10%.
- В пути: у ~30% sku, у 2–3 штук ETA уже прошёл.
- BOM: 3 комплекта «щит в сборе» → автоматы + бокс + DIN-рейка.
- **Эталонные sku для демо и тестов** (они же на странице «Проверки»):
  - `DEMO-SEASON`: светильник с сильной зимней сезонностью
  - `DEMO-STOCKOUT`: кабель с 3 неделями отсутствия в прошлом месяце
  - `DEMO-ONEOFF`: автомат, у которого нерегулярный клиент разово купил 20× обычного объёма
  - `DEMO-GROWTH`: розетка с устойчивым ростом +4%/мес
  - `DEMO-TRANSIT`: большая поставка в пути, заказ не нужен
  - `DEMO-CRITICAL`: остаток на 5 дней при сроке поставки 30

Если партнёр пришлёт отчёт V2: Никита в час 4 пишет маппинг колонок в `io.py` (словарь `{колонка партнёра: наша}`). Ядро остаётся без изменений.

## 6. Приёмочные тесты = проверки из трека (`tests/test_acceptance.py`)

| # | Must-have | Тест | Порог |
|---|---|---|---|
| 1 | Все источники влияют на результат | Для sku поочерёдно меняем: in_transit +500, on_hand −50%, growth +20%, категорию (другие сезонные индексы), удаляем stockouts, удаляем BOM-продажи. Каждый раз `recommended_qty` (или `need_raw`) меняется | ≠ базе для каждого источника |
| 2 | Сезонность | `DEMO-SEASON`: прогноз пикового месяца / прогноз провального > 1.5; WAPE модели < WAPE среднего | оба условия |
| 3 | Упущенный спрос | `DEMO-STOCKOUT`: `need_raw` со stockouts > `need_raw` без файла stockouts | строго больше |
| 4 | Разовые заказы | Добавляем в данные разовую строку 50× медианы от нового клиента → `recommended_qty` вырос не более чем на 10% | ≤ +10% |
| 5 | Группировка и обоснования | Нет пустых `explanation`; `groupby(supplier_id)` отдаёт все позиции; сумма по поставщикам = общая сумма | все |
| + | Устойчивость к мусору | Пустой sales, мусорные строки, отрицательные остатки → понятная ошибка/предупреждение, а не падение | без исключений |

Страница **«Проверки»** в UI запускает те же сценарии и показывает «до / после» цифрами и графиком. Это главный слайд демо: мы показываем выполнение must-have вживую, а не рассказываем о нём.

```bash
pytest -q
```

## 9. Git-процесс

- Работаем прямо в `main`, без PR (нет времени на ревью). Коммит минимум раз в 45 минут.
- Перед пушем: `git pull --rebase`, `pytest -q` (с 16:00), `streamlit run` не падает.
- Сообщения: `feat: …`, `fix: …`, `docs: …`, `test: …`.
- Только в свои файлы (раздел 2). Конфликт в чужом файле — пишем владельцу, сами не резолвим.
- Никита в :55 каждого часа проверяет, что `main` запускается целиком.
- Секреты не коммитим, в `.env.example` только имена переменных.

## 10. Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Данные партнёра не придут или придут в другом формате | высокая | Всё строим на синтетике (трек это разрешает). Адаптер колонок в `io.py`, ядро не трогаем |
| Прогноз даёт мусор на коротких/редких рядах | средняя | Сезонность категории, флаги `new`/`intermittent`, `confidence=low`, клипы на тренд и сезонность |
| Постоянного крупного клиента ошибочно считаем разовым | средняя | Условие «нерегулярный клиент» (≤ 2 месяцев покупок) |
| Двойной счёт роста (тренд + прирост менеджера) | средняя | В README и UI прямо написано: прирост = *дополнительный* плановый (контракты, промо), по умолчанию 0 |
| Интеграция в последний час ломает main | средняя | Контракт с 13:30, заглушка, E2E к 15:00, freeze в 17:00 |
| Streamlit тормозит | низкая | `cache_data`, ~150 sku × 36 мес — это копейки |
| Уход в «логистику» из слов оператора | средняя | Раздел 0: берём только то, что ложится на трек |
| Не успели README с методологией (обязательный артефакт) | средняя | У Абдуали это отдельный слот 16:00–17:00, не «потом» |
