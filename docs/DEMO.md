# Демо и питч — Амир

## Статус и честный показ

Это сценарий целевого интегрированного приложения из PLAN.md. Перед показом проверить фактический результат на текущей версии ядра. Не называть приложение полностью готовым и не обещать «5/5», пока живые проверки не подтвердили это. UI подключён к ядру команды. Полный сценарий проверяется на синтетике; результаты не являются доказательством качества на реальных данных партнёра.

Данные обозначать как синтетические, если используются `data/demo`. Не заявлять экономию, точность или успешную загрузку в реальную 1С без измерения. XLSX — файл согласованного формата для дальнейшего импорта, не прямая интеграция с 1С.

## Перед выходом (5 минут)

1. Запустить приложение, выбрать демоданные, дату 23.09.2026 и склад, где есть эталонные SKU. Выполнить расчёт.
2. Включить «Быстрый доступ к DEMO-позициям»: здесь доступны `DEMO-ONEOFF`, `DEMO-STOCKOUT`, `DEMO-CRITICAL` и `DEMO-TRANSIT`, включая позиции без заказа.
3. Выполнить «Проверки», записать **фактические** результаты и WAPE. Если есть красный/белый статус, исправить с владельцем ядра или открыто объяснить ограничение.
4. Вернуться к заказам, указать имя, утвердить тестовый заказ, скачать и открыть XLSX. Сравнить количество, артикул, склад и поставщика с экраном.
5. Повторить расчёт для чистого экрана демо. Сохранённый тестовый JSON останется в журнале. Проверить, что браузер и приложение работают без внешних API.

## Импорт партнёрских файлов (отдельно от трёхминутной синтетической проверки)

«Загрузить файлы» → выбрать комплект XLSX → показать распознанные типы → указать
реальные сроки поставки/цикл → проверить дату среза и ограничения → подтвердить
настройки → «Подготовить данные» → «Рассчитать». Один файл «В пути» показывает,
что ещё требуется. См. [IMPORT.md](IMPORT.md).

Объяснить, что нет клиентов, точных периодов отсутствия, BOM и полноценного
журнала движений остатков. Это сводный расчёт с низким доверием; нельзя переносить
«5/5» с синтетики на реальные файлы. Переход к реальным закупкам требует проверки
менеджером и актуализации остатков. Исходные коммерческие строки не включать в
скриншоты для публикации.

## Питч без интерфейса (около минуты)

«Мы — Null Talisman. Для менеджера закупа история продаж ещё не ответ на вопрос, сколько заказать. Один крупный проект может раздуть закупку, а отсутствие товара на складе — занизить оценку спроса.

Наше решение рассчитывает пополнение с учётом очищенной истории, сезонности, роста, остатков, поставок в пути и ограничений поставщика. Менеджер получает заказ по каждому поставщику и обоснование каждой позиции. В карточке можно проверить историю и прогноз, изменить количество, утвердить и скачать файл для дальнейшего импорта в 1С.

Мы проверяем требования сценариями “до и после”, а не только показываем итоговую таблицу. Решение остаётся за человеком: приложение ничего не отправляет поставщикам автоматически. На демо используются синтетические данные; следующий шаг — валидация на данных партнёра».

Говорить о каждом пункте алгоритма как о реализованном только после подтверждения соответствующего модуля командой.

## Ответы на вопросы

- **Где AI?** Абдуали отвечает подробно, если спросят дальше:
  1. Прогноз — не LLM, а детерминированная статистика (Theil–Sen тренд, сезонность к CMA-12, robust-z очистка выбросов). Это сознательный выбор ради объяснимости: трек требует показать «алгоритм исключения выбросов», а не просто дать число из чёрного ящика.
  2. Модель проверяет себя сама: backtest на 3 отложенных месяцах, WAPE против наивного среднего — на `DEMO-SEASON` модель в ~2 раза точнее (35% против 77% WAPE).
  3. LLM-кредиты (OpenAI/NVIDIA) выделены организаторами, но опциональный черновик письма пока не подключён. Не заявлять использование API: приоритет получили импорт и надёжность основного сценария.
  4. Интерфейс и экспорт полностью работают без LLM и API-ключей — ядро не деградирует при их отсутствии.
- **Почему такое количество?** Открыть обоснование: горизонт, прогноз, запас, остаток, в пути и округление. Затем график.
- **Как измерена точность?** Показать фактический WAPE и сравнение с наивным средним на отложенных месяцах. Не обобщать синтетику на реальные закупки.
- **Что с персональными данными?** Показать поведение подключённого загрузчика и подтвердить обезличивание. UI не выводит таблицу клиентов.
- **Почему нет суммы в тенге?** В базовом контракте нет закупочных цен. Мы не подменяем их ценами продажи; поле включается при передаче `purchase_price`/`unit_cost`.
- **Это уже интегрировано с 1С?** Есть XLSX/CSV согласованного формата. Прямая интеграция и проверка конкретной конфигурации 1С — следующий этап.
- **Что при ручной правке после утверждения?** Продемонстрировать исчезновение кнопок экспорта и повторное утверждение. Старое подтверждение остаётся в журнале.
- **Что с доставкой и GPS?** Учитываем количество в пути, ETA и просрочку. Маршруты и GPS вне текущего кейса; возможная будущая связка с TMS.

## Если что-то не работает

- Нет ядра/демоданных: показать понятное сообщение, не выдавать тестовый контракт за расчёт. Передать Никите требования из `app/README.md`.
- Невалидные входные файлы: показать предупреждение и вернуться к проверенным демоданным.
- Нет годового прогноза или эталонного SKU: белый статус «Недостаточно данных»; не считать требование подтверждённым.
- XLSX не открывается на компьютере жюри: скачать CSV UTF-8 BOM (`;`) и проверить количество.
- Нет времени: сохранить главную цепочку «расчёт → объяснение → правка → утверждение → файл», убрать аналитику.
